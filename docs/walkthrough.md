## 0. Минимум RL, без которого код не читается

**Обучение с подкреплением (RL)** — это цикл «агент ↔ среда»:

```
            действие a_t
  Агент  ─────────────────▶  Среда
    ▲                          │
    └──── наблюдение o_{t+1}, награда r_t, флаг «эпизод кончился» ◀┘
```

- **Среда (environment)** — «мир» с правилами. У нас это лабиринт.
- **Агент** — то, что выбирает действия. У нас это нейросеть.
- **Эпизод** — одна попытка от старта до конца: агент дошёл до цели или кончилось время.
- **Награда (reward)** — число, которое среда выдаёт после каждого шага. У нас 1 за попадание в цель, иначе 0.
- **Отдача (return)** — сумма наград за эпизод, обычно с дисконтом γ (гамма): `G = r_0 + γ·r_1 + γ²·r_2 + …`. При γ = 0.99 награда, полученная через 10 шагов, стоит 0.99¹⁰ ≈ 0.90, а через 50 шагов — уже ≈ 0.61. Поэтому агенту выгодно идти к цели **кратчайшим** путём, хотя сама награда за длину пути не штрафует.
- **Стратегия (policy) π** — правило выбора действия: «в такой ситуации с такой вероятностью иду вправо». Именно её мы и обучаем.

**MDP и POMDP.** Если агент видит всё, что нужно для оптимального решения (например, свои координаты), задача называется **MDP**. Если видит только часть (у нас — **цвет клетки**, а одинаковых цветов много), это **POMDP** — частично наблюдаемая задача. В POMDP по одному наблюдению «я на синей клетке» непонятно, где ты, потому что синих клеток пять. Чтобы понять это, приходится помнить, что видел и куда ходил раньше. Отсюда главная идея всего задания: **агенту нужна память** (рекуррентная сеть, GRU).

## 1. Файлы проекта и инфраструктура

### `pyproject.toml`

Паспорт Python-проекта: имя, версия Python, зависимости.

- `dependencies` — то, без чего проект не работает: `gymnasium` (стандартный интерфейс RL-сред), `numpy`, `matplotlib`.
- `torch` вынесен в **extras** `cpu` и `cu126`. **Зачем:** PyTorch бывает в двух сборках, для процессора и для видеокарты NVIDIA (CUDA). На ноутбуке без NVIDIA нужна первая, на компьютере с RTX 3050 вторая. Одна команда ставит то, что нужно:
  ```bash
  uv sync --extra cpu     # здесь
  uv sync --extra cu126   # на машине с GPU
  ```
- `[tool.uv.sources]` и `[[tool.uv.index]]` говорят uv, откуда брать каждую сборку torch: с официального сервера PyTorch, у каждого варианта свой адрес.
- `conflicts` запрещает ставить обе сборки одновременно.
- **Почему CUDA 12.6, а не новее:** для неё на сервере есть та же версия torch, что и для CPU (2.14.1), а требования к драйверу видеокарты у неё мягче (≥ 560). Значит, на обеих машинах код ведёт себя одинаково.

### `uv.lock`

Автоматически сгенерированный список **точных** версий всех пакетов. Благодаря ему на другой машине установится ровно то же самое. Руками его не правят.

### `.python-version`

Версия Python (3.12). uv сам скачает её, если на машине такой нет. 3.12 выбрана как самая «безопасная»: под неё есть готовые сборки всех библиотек.

### `.gitignore`

Что не кладём в git: виртуальное окружение `.venv`, кэши, папку с результатами экспериментов `runs/`, веса моделей `*.pt`, PDF с заданием.

Это стандартная «src-раскладка». Пакет `gridrl` устанавливается в окружение, и `from gridrl.envs import make_env` работает откуда угодно: из тестов, скриптов, ноутбуков. Без неё импорты ломаются в зависимости от того, из какой папки запускаешь.

## 2. `src/gridrl/envs/gridworld.py` — сама среда

### Почему `gymnasium.Env`

Gymnasium — стандартный интерфейс RL-сред. У любой среды есть:
- `reset()` → `(наблюдение, info)`: начать новый эпизод;
- `step(action)` → `(наблюдение, награда, terminated, truncated, info)`: сделать шаг;
- `observation_space` / `action_space` — описание того, как выглядят наблюдения и действия.

Если соблюдать этот интерфейс, со средой работают любые готовые инструменты: векторизация (`SyncVectorEnv`, задача 4), проверка корректности (`check_env`), обёртки.

### Константы наверху

```python
UP, RIGHT, DOWN, LEFT = 0, 1, 2, 3
ACTION_DELTAS = ((-1, 0), (0, 1), (1, 0), (0, -1))
```

Действия пронумерованы по часовой стрелке, начиная с «вверх», как требует задание. `ACTION_DELTAS[a]` — на сколько меняются `(строка, столбец)`. «Вверх» = строка −1, потому что строка 0 находится сверху.

### `__init__`: параметры и проверки

Параметры совпадают с заданием:

| Параметр | Что это |
|---|---|
| `floor_colors` | 2д массив `(h, w)` с покраской пола, числа от 0 до `n_colors-1` |
| `pos_goal` | координаты цели `(row, col)` |
| `n_colors` | сколько цветов пола (если не указано, берётся максимум + 1) |
| `obstacle_mask` | 2д массив `True/False`, где стоят препятствия |
| `pos_agent` | где агент стартует: `None`, точка или массив весов |
| `see_obstacle` | что видит агент, когда врезается в стену |
| `max_steps` | лимит шагов эпизода |
| `obs_mode` | `"color"` (по заданию) или `"coords"` (отладка) |

В начале много `raise ValueError(...)`: размеры совпадают, цель не на препятствии, цвета в допустимом диапазоне. **Зачем:** ошибку в параметрах лучше поймать сразу при создании среды, а не через час обучения, когда агент «почему-то не учится».

### Коды цветов

```python
self.goal_color = self.n_colors       # цель
self.obstacle_color = self.n_colors + 1
self.wall_color = self.n_colors + 2
self.n_obs_colors = self.n_colors + 3
```

Цвета пола занимают коды `0..n_colors-1`, следующие три кода — служебные. Итого `n_colors + 3` возможных наблюдений, ровно как в задании.

### Трюк с рамкой стены

```python
self.color_map = np.full((self.h + 2, self.w + 2), self.wall_color)
self.color_map[1:-1, 1:-1] = ...  # внутренность
```

Карта хранится на 2 клетки шире и выше: по краю идёт рамка из стены. **Зачем:** когда агент стоит у края и шагает наружу, мы просто смотрим в соседнюю клетку массива, а там стена. Не нужны проверки «не вышли ли за границу», и стена естественно получает свой цвет. Поэтому внутри класса координаты сдвинуты на +1 (`self._pos`), а наружу (в `info["pos"]`, `agent_pos`) отдаются обычные, без рамки.

`self.passable` — такой же массив `True/False`: можно ли встать на клетку. Стена и препятствия — `False`.

### `_start_distribution`: откуда стартует агент

Превращает `pos_agent` в вероятность стартовать из каждой клетки:
- `None` — равномерно по всем свободным клеткам, кроме цели;
- `(row, col)` — всегда из одной точки;
- массив весов `(h, w)` — на него накладывается маска (на препятствии и на цели стартовать нельзя), затем веса делятся на сумму. Это и есть L1-нормировка: вероятности в сумме дают 1.

Цель исключена, потому что старт на цели дал бы эпизод длины 0.

### `observation_space` и `action_space`

```python
spaces.Box(0.0, 1.0, shape=(obs_dim,), dtype=np.float32)
spaces.Discrete(4)
```

Наблюдение — вектор из нулей и одной единицы (**one-hot**): единица стоит на месте номера цвета. **Почему one-hot, а не просто число «цвет = 3»:** цвета не упорядочены. Цвет 3 не «больше» цвета 2, а если подать в нейросеть число, она будет считать именно так. One-hot делает все цвета равноправными.

### `reset`

1. `super().reset(seed=seed)` настраивает генератор случайных чисел `self.np_random`. С одним и тем же `seed` старт будет одинаковым, а значит, эксперименты воспроизводимы.
2. Выбирается стартовая клетка по `start_probs`. Через `options={"pos": (r, c)}` её можно задать вручную, это нужно в тестах.
3. Возвращаются наблюдение (цвет стартовой клетки) и `info`.

### `step`: один шаг

```python
target = (r + dr, c + dc)          # куда хотим шагнуть
bumped = not self.passable[target] # врезались?
if not bumped:
    self._pos = target
seen = target if bumped and self.see_obstacle else self._pos
```

- Если впереди стена или препятствие, агент остаётся на месте (`bumped = True`).
- Что агент **видит** после шага, решает флаг `see_obstacle`:
  - `True` (по умолчанию) — цвет препятствия, в которое врезался. Так агент узнаёт «там стена», и это полезная информация для ориентирования;
  - `False` — цвет своей клетки, как будто ничего не произошло.

**`terminated` и `truncated` — важное различие:**
- `terminated = True` — эпизод закончился «по-настоящему»: агент дошёл до цели. Будущих наград больше нет.
- `truncated = True` — эпизод **оборвали** по лимиту времени (`max_steps`). Агент не провалился, его просто остановили, и если бы эпизод продолжился, награду ещё можно было бы получить.

Алгоритмы обучения обрабатывают эти случаи по-разному (см. раздел про PPO), поэтому Gymnasium их и разделяет.

### `info`

Словарь с отладочной информацией: настоящая позиция `pos`, код цвета, `bumped`. **Агенту при обучении его не показываем**, иначе он узнает координаты и задача перестанет быть POMDP. `info` используется только для графиков, тепловых карт и тестов.

### `obs_mode="coords"`

Отладочный режим: вместо цвета агент видит one-hot своей позиции, то есть задачу MDP. Если агент **не учится даже здесь**, ошибка в коде алгоритма, а не в сложности задачи.

### `render`

- `"ansi"` — текстовая картинка (`#` стена, `X` препятствие, `G` цель, `A` агент, цифры и буквы — цвета пола). Удобно в терминале.
- `"rgb_array"` — картинка-массив пикселей, из неё потом соберём GIF траектории для отчёта.

## 3. `src/gridrl/envs/setups.py` — карты и четыре сетапа

### Генераторы карт

- `random_floor_coloring(h, w, n_colors, rng)` — каждой клетке случайный цвет. Хелпер, который просит задание.
- `unique_floor_coloring(h, w, rng)` — у каждой клетки свой цвет (перестановка чисел 0..h·w−1). Нужен для сетапа 1, где задача полностью наблюдаема.
- `random_obstacle_mask(h, w, fraction, rng)` — ставит `fraction·h·w` препятствий в случайные места и проверяет, что **все свободные клетки связаны**. Если препятствия отрезали кусок карты, пробует заново. **Зачем:** иначе агент мог бы стартовать в «кармане», откуда до цели не дойти, и задача стала бы нерешаемой.

### `rng: np.random.Generator`

Генераторы принимают объект-генератор случайных чисел, а не используют глобальный `np.random`. Тогда `build_setup(3, seed=0)` **всегда** создаёт одну и ту же карту, и у всех экспериментов одинаковые условия.

### `SETUPS` и `build_setup`

```python
SETUPS = {
    1: (5, 5, None, 0.0),   # 25 уникальных цветов: MDP
    2: (5, 5, 5, 0.0),
    3: (10, 10, 7, 0.1),
    4: (10, 10, 4, 0.1),
}
```

`build_setup(setup_id, seed)` по номеру сетапа собирает словарь параметров для `GridWorldEnv`: покраску, препятствия, случайную цель. `make_env(setup_id, seed, **overrides)` сразу создаёт среду, а через `overrides` можно поменять что угодно, например `make_env(2, see_obstacle=False)`.

Побочный эффект, который нам на руку: при одном `seed` у сетапов 3 и 4 **одинаковые** карта препятствий и цель, отличается только покраска. Сравнение «7 цветов против 4» получается честным.

### `bfs_distances` — поиск в ширину

Считает кратчайшее расстояние от одной клетки до всех остальных: сначала соседи на расстоянии 1, затем их соседи на расстоянии 2, и так далее. Используется дважды:
1. проверить связность карты (все свободные клетки достижимы);
2. посчитать оптимум.

### `optimal_stats` — «идеальный агент» для сравнения

Считает, сколько получил бы агент, который **знает свои координаты** и всегда идёт кратчайшим путём: средняя длина пути и средняя дисконтированная отдача (`γ^(d−1)`, где d — длина пути). Среднее берётся по всем стартовым клеткам с их вероятностями.

**Зачем:** без ориентира непонятно, хорош ли результат «агент дошёл за 9 шагов». Если оптимум 7.5 шагов, это неплохо. Для сетапа 1 (MDP) это достижимый потолок, для POMDP — верхняя граница: без координат агенту иногда приходится «осматриваться», так что он неизбежно будет чуть хуже.

## 8. Агенты: папка `src/gridrl/agents/`

Всё, что относится к **решателям** (нейросети и алгоритмы обучения), лежит отдельно от среды. Среда ничего не знает об агентах, агенты получают от среды только наблюдения и награды. Позже рядом появится `dsac.py`.

```
src/gridrl/agents/
  networks.py   # нейросети: Core (MLP или GRU) и ActorCritic
  ppo.py        # алгоритм PPO: сбор опыта, GAE, обновление, логи
scripts/
  train_ppo.py  # запуск обучения из командной строки
```

### 8.1. Что такое актор-критик

У агента две «головы» над общим телом:
- **актор** выдаёт стратегию: вероятности 4 действий (через логиты и softmax);
- **критик** выдаёт **V(s)** — оценку «насколько хорошо сейчас моё положение», то есть ожидаемую будущую отдачу.

Критик нужен, чтобы понять, было ли действие **лучше или хуже обычного**. Эта разница называется **преимуществом (advantage)**: `A = (что реально получили) − V(s)`. Если A > 0, действие оказалось лучше ожидаемого, и его вероятность повышаем; если A < 0, понижаем.

### 8.2. `networks.py`

**`Core`** — «тело» сети, переводит наблюдение во внутренний вектор (латент) размера `hidden = 128`.

- `memory=False` — **бейзлайн без памяти**: `one-hot цвета → Linear → Tanh → Linear → Tanh`. Агент реагирует только на текущий цвет.
- `memory=True` — **с памятью**: на вход подаются цвет **и предыдущее действие** (тоже one-hot), затем `Linear → Tanh → GRU`.
  - **GRU** — рекуррентный слой. У него есть скрытое состояние `h`, которое переносится от шага к шагу: это и есть память. На каждом шаге GRU смешивает старое `h` с новым наблюдением.
  - **Зачем предыдущее действие:** агент увидел «синий». Если он перед этим шёл вправо, это одна синяя клетка, если вверх — другая. Без информации о действии память почти бесполезна: агент не знает, куда сдвинулся.
  - `starts` — флаг «начался новый эпизод». На таком шаге `h` обнуляется, чтобы память о прошлом эпизоде не мешала новому.
- `step(...)` — один шаг, используется при игре в среде.
- `unroll(...)` — прогон по целой последовательности шагов `(T, B, ...)`, используется при обучении на сохранённом опыте.

**Почему так просто, без сложного энкодера:** на входе one-hot длины 8–28. Один линейный слой уже полностью описывает такой вход, и усложнять незачем. Вся «сложность» задачи — в памяти, поэтому главное архитектурное решение здесь GRU.

**Почему 128:** в задании размер не задан. В 10x10 память должна «держать» гипотезу, на какой из ~90 клеток стоит агент, и 128 чисел для этого с запасом. Больше — медленнее и капризнее при обучении, выигрыша не ждём.

**`layer_init`** — ортогональная инициализация весов, стандартная для PPO (как в CleanRL). Голова актора инициализируется очень маленькими весами (`gain=0.01`), поэтому в начале все действия почти равновероятны и агент сразу активно исследует.

**`ActorCritic`** — `Core` плюс две головы: `actor` (Linear → 4 логита) и `critic` (Linear → 1 число V).

### 8.3. `ppo.py` — алгоритм

**PPO (Proximal Policy Optimization)** — актор-критик с одной хитростью: стратегию **нельзя менять слишком сильно за одно обновление**. Это делает обучение стабильным.

Одна итерация обучения (`update`) состоит из четырёх частей.

**1. Сбор опыта (роллаут).** Запускаем `num_envs = 16` копий среды одновременно (`SyncVectorEnv`) и играем `rollout_len = 128` шагов в каждой. Получается 16 × 128 = 2048 переходов. Для каждого шага сохраняем наблюдение, действие, его вероятность (`logp`), оценку критика (`value`), награду и признак конца эпизода.

- **Почему сразу несколько сред:** больше разнообразного опыта за итерацию, и это готовая основа для задачи 4 (векторизации).
- `AutoresetMode.SAME_STEP` — когда эпизод в одной из копий кончается, она сразу перезапускается. Последнее наблюдение законченного эпизода лежит в `info["final_obs"]`.
- **Обработка `truncated` (обрыв по времени):** агента остановили, но не наказали. Поэтому к награде прибавляем `γ · V(последнее наблюдение)`, то есть оценку того, что он получил бы, если бы продолжил. Это называется bootstrap. При `terminated` (дошёл до цели) будущего нет и ничего не прибавляем. Ради этого различия Gymnasium и разделяет два флага.

**2. Преимущества через GAE** (`compute_gae`). **GAE (Generalized Advantage Estimation)** считает преимущество как взвешенную смесь коротких и длинных оценок:

```
δ_t = r_t + γ·V(s_{t+1}) − V(s_t)        # «ошибка» критика на одном шаге
A_t = δ_t + γ·λ·δ_{t+1} + (γ·λ)²·δ_{t+2} + …
```

- `λ = 0` — смотрим на один шаг вперёд и доверяем критику: меньше шума, но больше смещения, если критик ошибается.
- `λ = 1` — смотрим до конца эпизода по реальным наградам: смещения нет, но шумно.
- `λ = 0.95` — стандартный компромисс.

Считается с конца роллаута к началу; на границах эпизодов (`dones`) цепочка обрывается. **Цель для критика** (`returns`) — это `A + V`.

**3. Обновление сети.** 4 эпохи проходим по собранным данным минибатчами.
- **Лосс актора (clipped):** `ratio = π_new(a) / π_old(a)` показывает, во сколько раз изменилась вероятность действия. Если ratio выходит за `[0.8, 1.2]` (`clip_coef = 0.2`), градиент обрезается, и стратегия не может «убежать» далеко за одно обновление. Это и есть суть PPO.
- **Лосс критика:** среднеквадратичная ошибка между V и целью `returns`.
- **Бонус энтропии:** энтропия — мера случайности стратегии. Небольшая награда за неё (`ent_coef = 0.01`) не даёт агенту слишком рано стать уверенным и перестать исследовать.
- Итог: `loss = policy_loss + 0.5·value_loss − 0.01·entropy`.
- **Минибатчи режутся по средам, а не по отдельным шагам:** для GRU нужны целые последовательности, иначе память не прогнать. Поэтому в минибатч идут все 128 шагов из 4 случайных сред, а прогон стартует с сохранённым на начало роллаута состоянием памяти `h_init`.
- `clip_grad_norm_` ограничивает величину градиента, тоже для стабильности.

**4. Логи.** После каждой итерации в `runs/<имя>/metrics.csv` пишется строка:

| Колонка | Что это |
|---|---|
| `global_step` | всего шагов среды (сумма по всем копиям) |
| `success` | доля эпизодов, дошедших до цели (это и есть недисконтированная отдача, она равна 0 или 1) |
| `return` | средняя дисконтированная отдача `γ^(длина−1)`, сравнивается с оптимумом |
| `ep_length` | средняя длина эпизода |
| `loss`, `policy_loss`, `value_loss` | полный лосс и его компоненты |
| `entropy` | энтропия стратегии |
| `explore_prob` | вероятность нежадного действия `1 − max π(a)`: насколько агент ещё «пробует» |
| `approx_kl`, `clipfrac` | насколько сильно меняется стратегия за обновление (диагностика PPO) |

Рядом сохраняются `config.json` (все параметры и оптимум для сравнения) и `model.pt` (веса сети).

### 8.4. `scripts/train_ppo.py`

Превращает поля `PPOConfig` в аргументы командной строки, поэтому любой параметр можно поменять при запуске:

```bash
uv run python scripts/train_ppo.py --setup 1 --no-memory

```

### 8.5. Первые результаты (дымовые прогоны, один сид)

| Сетап | Агент | Шагов | Отдача | Оптимум | Длина эпизода | Оптимальная длина |
|---|---|---|---|---|---|---|
| 1 (MDP) | без памяти | 100k | 0.977 | 0.977 | 3.4 | 3.3 |
| 2 (POMDP) | без памяти | 300k | 0.959 | 0.975 | 5.3 | 3.5 |
| 2 (POMDP) | GRU | 300k | 0.972 | 0.975 | 3.8 | 3.5 |

- На сетапе 1 агент без памяти выходит на оптимум: алгоритм работает.
- На сетапе 2 оба доходят до цели всегда, но **агент с памятью ходит заметно короче** (3.8 против 5.3 шага). Без памяти агент «блуждает», пока не узнает знакомые цвета, а с памятью быстрее понимает, где находится.
- Минус GRU: он примерно в 6 раз медленнее (~1000 шагов/с против ~6000), потому что память приходится прогонять шаг за шагом в цикле.
